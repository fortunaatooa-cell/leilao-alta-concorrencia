    2 · Desenho

    Arquitetura na AWS

    Poucos serviços, todos gerenciados. O caminho que responde ao usuário é curto, e o resto é assíncrono. A versão com os ícones oficiais da AWS abre no diagrams.net: abrir o desenho editável.

    1. Lance: o usuário envia o valor com um lance_id único.
    2. Decisão: a Lambda grava no DynamoDB só se a versão do leilão não mudou.
    3. CDC: cada gravação vira evento no Kinesis e vai bruta para a SOR no S3.
    4. SOR → SOT: o Glue deduplica, reordena, pseudonimiza e roda Data Quality.
    5. SOT → SPEC: visões prontas por área, em tabelas Iceberg.
    6. Consumo: Athena e QuickSight, com acesso governado pelo Lake Formation.
    ① Transacional. O lance só é aceito quando o DynamoDB grava com condição: a versão do leilão não mudou e o lance_id ainda não existe. A ordem oficial é a ordem desses commits.
    ② SOR. Cada gravação vira evento pelo DynamoDB Streams (CDC). Não existe evento perdido entre decidir e publicar. Chega duplicado e fora de ordem, e tudo bem.
    ③ SOT e SPEC. Glue deduplica, reordena, pseudonimiza e roda Data Quality, inclusive a reconciliação com o DynamoDB. Lake Formation controla quem vê o quê.
    3 · Explicação

    Como funciona, passo a passo

    O problema: race condition

    Ana e Beto leem o mesmo preço e mandam o mesmo valor. Sem proteção, os dois são aceitos.

    Ana lê preço = 100 Beto lê preço = 100 Ana grava 101 Beto grava 101 resultado: dois vencedores

    A solução: escrita condicional

    Grava só se ninguém mudou o leilão desde a leitura. Quem perde a corrida relê e é reavaliado.

    Ana grava (versão 0) OK → versão 1 Beto grava (versão 0) FALHA: versão mudou Beto relê: 101 não supera 101 + R$ 1 resultado: um vencedor, ordem definida

    Perguntas frequentes

    Por que não ordenar pelo horário do celular?

    O relógio do cliente pode estar errado ou ser manipulado. Quem define a ordem é o servidor, no momento em que grava. A SOT usa essa sequência para reordenar.

    Se o transacional já é idempotente, por que deduplicar de novo na SOT?

    São garantias diferentes. O transacional garante uma decisão por lance. O stream pode entregar a mesma decisão mais de uma vez. Cada camada protege a própria fronteira.

    Como saber que o dado analítico está certo?

    Regras de Data Quality rodam a cada carga. A principal compara o preço final da SPEC com o preço no DynamoDB. Se divergir, um alarme dispara.

    E a LGPD?

    O lake não guarda o id real do usuário, só um pseudônimo (hash com sal). A chave fica no Secrets Manager e o Lake Formation restringe colunas.

    E se um leilão receber 100 mil lances por segundo?

    Uma chave do DynamoDB aceita cerca de 1.000 escritas por segundo. A API recusa na hora quem está abaixo do preço atual, usando um cache, e só os lances plausíveis chegam à escrita condicional.
